# Multiple weddings and manually shared invitation codes

**Status:** Implemented on 12 November 2026 after user authorization, including the guarded development database migration. This document remains the delivery contract; PROJECT_STATUS.md records verification and remaining dependencies.

This amendment supersedes the single-wedding-per-account and email-only management-invitation rules. The PRD, architecture, API and database documents describe the target behavior; PROJECT_STATUS distinguishes it from the working baseline. Deliver this as one complete, reviewable feature rather than stopping after sending or after code generation.

## 1. User experience and binding choices

- One management account can create or join several weddings. A person can be an administrator in one and an organizer in another; permissions never carry between them. Each wedding still has independent records and at least one active administrator.
- After registration or sign-in, open **Your weddings** at `/weddings`, including when there is only one wedding. Cards show title, couple/host names, wedding dates/time zone and the user's role, with an explicit **Open wedding** action. No weddings is a useful empty state with **Create wedding** and **Join with code**, not an error.
- Creating or joining another wedding is available regardless of existing memberships. A duplicate invitation to a wedding already joined gives **You already belong to this wedding** and an Open wedding action; it never creates a duplicate membership or changes the existing role.
- The wedding header shows the selected wedding and a switcher. Wedding selection belongs to the URL/browser tab, not a mutable account-wide or session-wide current-wedding setting. Switching one tab cannot change another tab's destination or pending form.
- Every management invitation still requires an intended recipient email and an admin-selected role. This address binds redemption to the intended account even when the code is shared manually. No membership comes from email matching alone; manual delivery proves possession of an admin-issued code, not mailbox verification.
- Admins choose **Share code manually** or **Send email**. Manual generation does not call Resend, require Resend credentials/a verified sending domain or consume an email allowance. Email remains available with the existing editable subject/message dialog. Provider failure does not prevent sharing an already-created active code.
- Codes remain case-sensitive, random 12-character, single-use and expiring (24 hours, 48 hours or seven days, default 48 hours). Showing or copying an active code does not consume it, change its role, extend expiry or generate a replacement.
- Pending cards mask codes. Admins explicitly Show code/Copy code in a private dialog with recipient, role, expiry and a sharing warning. Organizers and recipients cannot reveal a management code through this admin control. No management capability links, code-bearing URLs, public invite lookup or automatic email-based joining.
- A fresh replacement invalidates the previous unused code for the same wedding/recipient. Revocation, consumption and expiry prevent both joining and further reveal. A recipient signs in/registers using the invited email, enters the code, then chooses **Open this wedding** or **View all weddings** after success.

## 2. Routes and wedding context

| Browser route                                          | Purpose                                                                                   |
| ------------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| `/weddings`                                            | Account's wedding selector; paginated list/search, empty/loading/recoverable-error states |
| `/weddings/new`                                        | Create another wedding; available with zero or several memberships                        |
| `/weddings/join`                                       | Join by code; available with zero or several memberships                                  |
| `/weddings/{weddingId}`                                | Selected wedding overview                                                                 |
| `/weddings/{weddingId}/functions`, `/details`, `/team` | Existing management features in an explicit wedding context                               |

Legacy `/wedding`, `/wedding/functions`, `/wedding/details` and `/wedding/team` go to the selector rather than guessing the first membership. Legacy setup/join routes redirect to their new account-level counterparts. Update all links, authentication destinations, email instructions and redirect tests together. Opening or refreshing a scoped URL validates access; a foreign/nonexistent/removed wedding shows safe access feedback and a way back to Your weddings.

Retain existing singular business API routes to limit unrelated rewrites, but require `X-Wedding-Id` on every tenant-owned management request. The route's wedding ID is only a candidate. The server authenticates the account, validates that exact ACTIVE membership and ACTIVE wedding, derives that wedding's role and scopes all referenced records. No fallback to the first membership and no server-wide `activeWeddingId`. Auth, account wedding listing, wedding creation and invitation redemption are context-free exceptions; guest/vendor capabilities remain unchanged.

Use a centralized client request helper scoped to the route ID. Query keys, cached data, forms, optimistic changes, abort controllers and error reconciliation must include that ID. Clear old wedding data before showing another wedding, cancel obsolete requests and ignore late responses from the old context. Never redispatch an old draft or failed write under a newly selected wedding. Warn before discarding unsaved changes. Preserve financial/function revisions and the existing wedding/date/time-zone constraints inside each wedding.

An admin removing a member or changing a role affects only that membership. Revalidate membership on every request; serialize critical writes and membership revocation through the same wedding transaction lock so authorization cannot remain stale at commit. Do not sign the account out of unrelated weddings. Account-level logout, password recovery/compromise and disabling an account retain their authentication-wide rules. On invitation acceptance, rotate the current session rather than revoking unrelated sessions; the session authenticates identity, not a global wedding or role.

## 3. API contracts

All unsafe requests keep existing Origin/CSRF checks. Protected responses use `Cache-Control: no-store`; IDs, roles and membership claims from the browser never authorize themselves.

| Endpoint                                            | Planned behavior                                                                                                                                                                                                                                                        |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/v1/auth/me`                               | `{data:{user,weddingCount}}`; count includes only accessible ACTIVE weddings; no arbitrary single `membership`                                                                                                                                                          |
| `GET /api/v1/weddings`                              | Account-level, cursor-paginated membership-backed wedding cards; default 20/max 100; optional bounded text search; no records from other accounts                                                                                                                       |
| `POST /api/v1/weddings`                             | Signed-in accounts may create another wedding plus first-admin membership atomically. Require a persisted UUID Idempotency-Key: same attempt cannot create duplicate weddings; different intentional creations are allowed                                              |
| `GET /api/v1/wedding`                               | Requires X-Wedding-Id; returns that wedding plus safe membership ID, role and revision for context                                                                                                                                                                      |
| Existing functions/details/team/member APIs         | Require exact X-Wedding-Id and scoped authorization; cross-wedding child IDs remain concealed as 404                                                                                                                                                                    |
| `POST /api/v1/member-invitations`                   | Admin/context required; recipient, role, expiry, optional subject/message and required deliveryMethod (MANUAL or EMAIL); safe metadata only                                                                                                                             |
| `POST /api/v1/member-invitations/{inviteId}/reveal` | Admin/context + CSRF + persisted reveal limit (starting 10/account/wedding/15 minutes). Recheck invitation validity; decrypt only that active invitation. `{data:{code,expiresAt}}` is the explicit secret-bearing exception; never expose verifier, ciphertext or keys |
| `POST /api/v1/member-invitations/redeem`            | Signed-in `{email,code}`, independent of currently open wedding. Existing memberships elsewhere are allowed. Consume and create/reactivate the target membership atomically; return safe membership/wedding summary, not the code                                       |
| `PATCH/DELETE /api/v1/members/{memberId}`           | Context/revision/admin required; only the selected wedding changes; last-admin rule per wedding                                                                                                                                                                         |

Manual invitations show `emailStatus: NOT_SENT` and **Email not requested**, independently of pending membership status. EMAIL uses existing quota/provider outcome handling; failed/unconfirmed sends retain the active code. A known configuration/quota rejection offers an explicit manual-generation fallback, not a false Sent state or a silent switch of modes. Reissue uses a new idempotent creation attempt and revokes prior pending codes within that wedding/recipient only. Email uniqueness and account identities stay global; invitation uniqueness/reissue is wedding-scoped.

Errors: missing context is `400 WEDDING_CONTEXT_REQUIRED`; malformed context is 400; nonexistent/foreign/removed contexts are indistinguishable 404. Known selected-wedding organizer admin attempts remain 403. Same-wedding duplicates use `409 ALREADY_A_MEMBER`, not the removed one-wedding `MEMBERSHIP_LIMIT`. Invalid/expired/revoked/used/wrong-account codes retain generic 422; throttles return 429 with Retry-After. Legacy active codes lacking recoverable ciphertext return `409 CODE_UNAVAILABLE` to an authorized admin with replacement guidance, never a guessed/reconstructed secret. Invalid or foreign reveal IDs remain 404; unauthorized role attempts 403.

## 4. Persistence, secret lifetime and migration

No new database collections are needed.

- Keep the unique `(weddingId,userId)` membership index and one lifetime row per pair. Rejoining reactivates that row and increments its revision. Replace the unique active `userId` restriction with a non-unique `{userId:1,status:1,weddingId:1}` listing index. Keep `{weddingId:1,status:1,role:1}` for scoped membership checks. Last-admin counting/guards remain inside serialized per-wedding transactions.
- Authentication sessions remain account-scoped. Do not persist a selected wedding as authority. An optional display preference must never select a tenant for writes; it is not required for this feature.
- Invitations add required `deliveryMethod`; recipient email remains required for both modes. Store a keyed code verifier and versioned AES-256-GCM `encryptedCode` recoverable for the entire active invitation lifetime, including after email provider acceptance. This intentionally replaces pending-delivery-only retention. Clear ciphertext atomically on consume, revoke or replacement. On expiry, refuse reveal/redeem immediately by expiresAt even before cleanup; a bounded maintenance cleanup removes expired ciphertext while audit metadata/history remain.
- Retain server-only external key material and compatible versioned derivation. Never expose codes in list/create DTOs, outbox rows, audit metadata, logs, analytics, query strings, HTML previews or browser storage. Secret reveal is an authenticated no-store POST, with no analytics/session replay on its dialog and audit of the action without the secret. Mask/clear in-memory display on close, short timeout (60 seconds), wedding switch and sign-out. Copy requires a user action; clipboard failure leaves a selectable code and safe feedback. The application cannot guarantee deletion of copies already shared outside it.
- Migrate existing encryptedDeliveryCode to encryptedCode without losing nonce/tag/keyVersion or changing compatible key derivation. Preserve verifier, record ID, recipient, expiry and consumption state. Historical email-accepted invitations whose ciphertext was deleted cannot be recovered from a hash; retain them and offer an explicit replacement. Do not silently issue codes or extend expiry during migration.

Migration sequence when implementation is authorized:

1. Inventory actual indexes and membership/invitation shapes; take a backup and verify there are no duplicate wedding/user pairs. Do not delete users, memberships, weddings or business records.
2. Prepare code that authorizes an explicit wedding and no longer calls findOne(userId) as tenant selection. Add the non-unique account listing index while retaining the pair uniqueness index. Prepare idempotent wedding creation so removing the old index cannot create accidental duplicate weddings from retries.
3. Use a coordinated deploy/maintenance window: stop old writers, remove only the verified legacy `one_active_wedding_per_user` unique restriction, deploy context-aware handlers/clients, migrate compatible invitation ciphertext, validate index definitions and reactivate traffic. Do not leave old implicit-tenant writers running beside multi-wedding membership data. No database work is authorized in this planning turn.
4. Smoke-test existing accounts/records before enabling new memberships and revealing migrated active codes. Keep migration retryable with an explicit report of changed indexes/fields, not a destructive reset.
5. Rollback is conditional: after users have multiple active memberships, the old unique index cannot safely be restored. Roll forward or pause new writes; restoring the old app/index is permitted only after a deliberate backup-based reconciliation, never deleting extra memberships automatically.

## 5. UI/UX design checklist

- Desktop Stitch design with coherent states: wedding picker with several/one/no cards; scoped header switcher; manual/email choice; required recipient email/role/expiry; centered masked/revealed/copy-success dialog; legacy-unrecoverable code; failed email/manual fallback; join while already in other weddings; success and already-member guidance; loading, access removed and recoverable error.
- Display a role beside each wedding, the selected wedding prominently in management pages and the recipient/role beside every revealed code. No design-review toggles or sample records become shipped application UI.
- Preserve current tokens, password controls, autocomplete, validation, duplicate-submit prevention, keyboard focus, Escape/cancel and reduced-motion behavior. Modals keep the existing centered 48%-dimmed/4px-blurred treatment, internal scrolling and mobile margins. Clear dirty-state warnings before context changes; never lose data silently.
- Mobile implementation review must use the actual routes at 390px and desktop 1440px; check long wedding names, email wrapping, selector navigation, focus trap/return, code visibility, copy fallback, scroll and horizontal overflow. Design artifacts are not proof of implemented or tested routes.

## 6. Delivery and verification gates

Implement migration, context-aware backend, selector/switcher, invitation reveal/manual mode and revised onboarding together, then deliver the full workflow for user review. Internal work packages are not separate partial feature handoffs. Preserve existing functionality and update all affected consumers of the old singular membership contract, including email instructions, auth navigation, wedding setup, functions, date editing, Team, test fixtures and future feature templates.

Required focused tests before calling the feature ready:

1. One account creates/joins weddings A and B; roles differ; membership lists include only authorized active weddings. Zero/one/many picker states and direct scoped routes work after reload and fresh sign-in.
2. Concurrent duplicate join to A yields one pair; simultaneous joins to A and B from independent active sessions both succeed. Rejoining a removed pair reuses its row. Concurrent creation using one idempotency key creates one wedding; different keys permit intentional separate weddings.
3. A foreign wedding or child ID, omitted header, mismatched header/child references, stale role and removed membership cannot read/write/reveal. The client request helper binds its header to the current scoped URL; a browser route or Referer is not server authorization evidence. Admin A has no admin power in B. Existing date-range, zone/revision and archive invariants hold independently in both weddings.
4. Two tabs editing different weddings retain their original targets while one tab switches/joins/creates another wedding. Old async responses, retries, optimistic data and dirty drafts never cross context. Removing access in A leaves B usable and does not globally log out the account.
5. Without any Resend configuration, an admin generates and reveals/copies a manual code; intended recipient signs up/signs in, joins the right wedding once and can select it. Same-code sharing still works after successful email, failed email or provider uncertainty. Manual actions consume no email quota and make no provider calls.
6. Code reveal rejects organizers/foreign IDs and invalid states; safe metadata never contains a code. Verify no-store headers, no logs/outbox/browser persistence, reveal throttling/CSRF, clipboard failure, mask timeout/close/switch, and invalidation on consume/reissue/revoke/expiry. Legacy missing ciphertext produces replacement guidance.
7. Per-wedding last-admin protection survives concurrent demotion/removal. Self-removal, access loss and role changes refresh the affected context without disturbing other weddings; no in-flight protected mutation can commit using revoked permissions.
8. Run affected unit, integration and Chrome flows, including desktop/mobile UI. This tenant-model migration justifies an application-wide regression checkpoint at completion. Record exact checks and real-provider limitations; no real email is required for the fully functional manual workflow.

**Completion boundary:** The complete manual-code and multi-wedding workflow is implemented for user review. Migration was applied to development after a private backup. Live arbitrary-recipient email still requires a verified sending domain; manual delivery has no email dependency.

Security clarification: each successful redemption consumes and rotates its exact current session transactionally. Concurrent requests using the same old cookie can receive 401 and must retry using an active session; revoked credentials never receive a rotation grace period.
